* Quantum programs as Lean data.
:PROPERTIES:
:CHAPTER: 01 / THE IDEA
:KICKER: 00:00–01:30

LeanQASM embeds an OpenQASM 3.0 frontend in Lean 4. It turns accepted source into a program that can be executed, inspected, and used in propositions.

The research goal is to connect a familiar quantum programming language with a proof assistant, while keeping the contracts between compilation, execution, and reasoning visible.

Today: one runnable example, the key design choices, the evidence already in the repository, and a concrete discussion of AI-assisted quantum software.

* The question is what each layer establishes.
:PROPERTIES:
:CHAPTER: 01 / THE IDEA
:KICKER: 01:30–02:30
:DURATION_SECONDS: 60

Lean can represent a program as ordinary data and check proofs about that data. A statement about its structure, a statement about its execution, and a statement about quantum behavior have different assumptions.

* Start with a circuit you recognize.

The =qasm! Bell= command embeds OpenQASM directly in a Lean document. It allocates two qubits and applies Hadamard followed by controlled X.

The command generates =Bell.program=, typed input/output structures, and =Bell.execute=. Target options and the opt-in dialect are explicit.

The intended ideal circuit prepares

\[
|\Phi^+\rangle
=\mathrm{CNOT}(H\otimes I)|00\rangle
=\frac{|00\rangle+|11\rangle}{\sqrt{2}}.
\]

That equation describes the intended quantum operation; the trace demonstration does not calculate or prove this state vector.

=Bell.execute= runs through =TraceBackend.M=. The example inspects the allocated qubits; the backend also records the unitary operations requested by the interpreter.

TraceBackend can supply scheduled measurement outcomes. This makes it useful for regression tests of control flow and backend effects.

It records operations and outcomes without modeling a physical quantum state or a noise process. A state-vector simulator would be a separate backend implementation.

The elaborator connects parsing, include expansion, dialect checks, type analysis, and lowering. Failures become Lean diagnostics.

Accepted source becomes =QASM.IR.Program=. The generated execute wrapper passes this data to the shared interpreter; it does not contain a separate copy of the source program as Lean control flow.

This gives tooling a stable object to inspect and transform. It also creates a clear place to state future compiler-correctness obligations.

* One IR connects several consumers.
:PROPERTIES:
:FILE: QASM/IR/Program.lean
:LINES: 33-49
:CHAPTER: 03 / THE DESIGN

=Program= collects declarations, typed inputs and outputs, target configuration, provenance, and the structured process body.

Execution, OpenQASM emission, and visualization consume this representation. They do not each reconstruct their own program from the original text.

For reasoning, the same representation is an ordinary Lean value. The representation enables precise statements; the implementation still needs proofs for whichever guarantees we want to claim.

* Preserve quantum circuit structure.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 33-45
:CHAPTER: 03 / THE DESIGN
:KICKER: 10:00–12:00
:DURATION_SECONDS: 120
:PRESENTER_NOTE: Use the mathematical structure as a bridge to the audience. Avoid implying that every raw Circuit is well-formed or that all categorical laws have been proved.
:END:
=Circuit= retains sequential composition, tensor, permutation, inversion, powers, and control as distinct constructors.

For sequential composition, the outer boundaries are

\[
\mathrm{dom}(g\circ f)=\mathrm{dom}(f),\qquad
\mathrm{cod}(g\circ f)=\mathrm{cod}(g).
\]

Input/output compatibility is a lowering responsibility: the raw constructors are not intrinsically indexed by matching interfaces. These are structural projections, not a denotational model of quantum states.

* Keep hybrid control flow explicit.
:PROPERTIES:
:FILE: QASM/IR/Proc.lean
:LINES: 117-129
:CHAPTER: 03 / THE DESIGN
:KICKER: 12:00–14:00
:DURATION_SECONDS: 120
:PRESENTER_NOTE: Explain why a circuit-only representation is insufficient. Use measurement-conditioned control as a motivating workflow, not a new benchmark or hardware claim.
:END:
Quantum programs also contain classical state, conditions, loops, and subroutine calls. =Proc= preserves that structure alongside effectful atomic operations.

The interpreter handles classical computation and structured control. Quantum allocation, gate application, measurement, reset, and barriers cross the backend boundary.

This separation is useful for measurement-conditioned workflows: reasoning about control and specifying quantum effects become identifiable, separate tasks.

* The backend boundary is small and explicit.
:PROPERTIES:
:FILE: QASM/Runtime.lean
:LINES: 252-257
:CHAPTER: 03 / THE DESIGN
:KICKER: 14:00–16:00
:DURATION_SECONDS: 120
:PRESENTER_NOTE: This is a useful discussion point for interoperability. Ask about a preferred integration target later; do not turn this into a promise of an existing Cirq or device backend.

=QuantumBackend= exposes five operations: allocate, apply, measure, reset, and barrier. Execution is polymorphic over the monad, qubit representation, and backend error type.

TraceBackend implements this interface today. An adapter to a simulator or another quantum toolchain is an integration task to evaluate, not an existing feature to assume.

The interface specifies how effects are requested. It does not itself impose the physical or probabilistic laws that a quantum correctness argument would require.

* Reason about a family, not only an instance.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 16-26
:CHAPTER: 04 / THE EVIDENCE
:KICKER: 16:00–18:00

Family binders introduce Lean parameters such as =n : Nat=. =Rotate.program n= retains the parameter, while =theta= is a separate runtime input.

This allows propositions quantified over all sizes instead of checking only selected numerical instances. Calling the generated program function does not reparse the QASM source.

The generated =Valid= predicate requires positive residual sizes. It establishes that size precondition; index safety, termination, and successful execution remain separate questions.

* A real theorem, with explicit assumptions.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 97-102
:CHAPTER: 04 / THE EVIDENCE
:KICKER: 18:00–20:30
:DURATION_SECONDS: 150
:PRESENTER_NOTE: Show the quantification over n and model, then the application of sequence_skip_left. Acknowledge that the law is deliberately simple: the point is the mechanism and its scope.
:END:
=rotate_skip_neutral= applies an existing program law to the whole open family. For every =n= and every supplied relational model, prefixing the body with =skip= preserves the model's execution relation.

\[
\forall n,\quad
\mathrm{Equivalent}_{M}
\bigl(\mathrm{sequence}[\mathrm{skip},\mathrm{body}_n],\mathrm{body}_n\bigr).
\]

This is a kernel-checkable theorem over program data, rather than a finite execution test. Its scope is a control-flow law relative to =M=; it does not establish a quantum algorithm's physical correctness.

* Separate proof semantics from the interpreter.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 24-39
:CHAPTER: 04 / THE EVIDENCE
:KICKER: 20:30–22:30
:DURATION_SECONDS: 120
:PRESENTER_NOTE: Be precise about the trusted boundary. If asked about end-to-end verification, point to the missing refinement and quantum semantic model instead of equating Lean implementation with verified behavior.
:END:
=Semantics.Model= supplies the meaning of operations, conditions, iteration domains, and related control-flow ingredients as relations on states.

=Exec= then describes finite successful control flow. =Equivalent= compares those relations for a fixed model.

The executable interpreter uses partial definitions. Refinement from that interpreter to the relational semantics remains an obligation, as do probabilistic and divergence-sensitive notions of quantum equivalence.

* Appendix: the support boundary.
:PROPERTIES:
:CHAPTER: APPENDIX / OPTIONAL
:KICKER: OPTIONAL / AFTER THE TALK
:DURATION_SECONDS: 0
:END:
Portable lowering covers typed classical values, arrays, structured control, gates, includes, and backend-facing quantum effects. Strict OpenQASM 3.0 is the default; =switch= and =nop= require the extended dialect.

| Target-dependent construct | Current portable elaboration |
|----------------------------+------------------------------|
| Calibration and OpenPulse bodies | Rejected with a capability diagnostic |
| Physical qubit names | Rejected with a capability diagnostic |
| Target-relative timing and scheduling | Rejected with a capability diagnostic |
| Extern ABI calls | Rejected with a capability diagnostic |

Parsing a construct and supporting its portable execution are different milestones. The detailed matrix is maintained in =CONFORMANCE.md=.

Current limitations include textual type diagnostics, incomplete handling of runtime-invalid classical indexing, and target-dependent numeric choices. =Valid= addresses positive residual sizes only.

Proof work remains on interpreter refinement, quantum/backend semantics, runtime safety, and richer behavioral equivalence. Device scheduling and noise models require additional target-specific work.
