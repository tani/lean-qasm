* From quantum code to statements about code.
:PROPERTIES:
:CHAPTER: 01 / LANGUAGES AND REPRESENTATIONS
:KICKER: 00:00–00:30
:DURATION_SECONDS: 30
:PRESENTER_NOTE: State the goal in 30 seconds. The definitions that follow are part of the technical argument, not introductory filler.
:END:
LeanQASM connects OpenQASM programs with Lean definitions, execution, and propositions about those definitions.

We will first define the languages and representations, then follow one example through them. The second half makes the proof targets concrete: which mathematical object is being discussed, what claim is stated, and what an existing proof establishes.

* Lean: programs, propositions, and proof terms.
:PROPERTIES:
:CHAPTER: 01 / LANGUAGES AND REPRESENTATIONS
:KICKER: 00:30–02:00
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Define proposition, proof term, and kernel checking. No assumption of prior Lean knowledge is needed; familiarity with programming and mathematics is enough.
:END:
Lean 4 is a dependently typed programming language and an interactive theorem prover. It can define data, compute with it, and express propositions about it.

A proposition \(P\) is represented as a type in =Prop=. A proof is a term \(h : P\), whose type is checked by Lean's kernel. Tactics help construct that term.

Here, Lean hosts three things: data describing quantum programs, code that processes that data, and proofs of explicitly stated properties. Implementing a program in Lean and proving a specification about it are separate tasks.

* OpenQASM: a language for hybrid computation.
:PROPERTIES:
:CHAPTER: 01 / LANGUAGES AND REPRESENTATIONS
:KICKER: 02:00–03:00
:DURATION_SECONDS: 60
:PRESENTER_NOTE: Establish what QASM denotes in the talk. Avoid explaining quantum gates themselves; focus on the role and scope of the programming language.
:END:
OpenQASM is a language for describing quantum operations together with the classical computation that controls them. This project targets OpenQASM 3.0.

A source program can declare qubits and classical variables, apply gates, measure, branch, loop, and call subroutines. Its portable part must be distinguished from features requiring a device-specific timing, calibration, or host model.

LeanQASM is an embedding of this language into Lean: it brings the source into a setting where its program representation can also be the subject of mathematical statements.

* Surface syntax: what the author writes.
:PROPERTIES:
:FILE: Examples/Bell.lean
:LINES: 38-47
:CHAPTER: 01 / LANGUAGES AND REPRESENTATIONS
:KICKER: 03:00–04:30
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Point out the boundary between Lean syntax and the embedded QASM text. Target/dialect options can be mentioned briefly rather than becoming another topic.

The outer =qasm! Bell { ... }= command is a Lean syntax extension. The text inside the braces is OpenQASM source, captured and processed by LeanQASM's elaborator.

The command generates ordinary Lean declarations:

- =Bell.program= is a value describing the resolved program.
- =Bell.Inputs= and =Bell.Outputs= describe its typed boundary.
- =Bell.execute= is a wrapper that runs the shared interpreter.

These names are how later Lean code refers to the embedded program. The surface notation and the generated program data have different roles.

* From source AST to resolved IR.
:PROPERTIES:
:FILE: QASM/Elaboration.lean
:LINES: 293-313
:CHAPTER: 01 / LANGUAGES AND REPRESENTATIONS
:KICKER: 04:30–06:00
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Define AST and IR before using their abbreviations freely. Explain parse, analyzeTypes and Lowering.template as the concrete steps.
:END:
An abstract syntax tree (AST) records the structure of the parsed OpenQASM source: declarations, expressions, statements, and their locations.

Type analysis resolves static information. Lowering translates the accepted AST into an intermediate representation (IR) whose declarations, expressions, types, and references are explicit.

Here, IR means LeanQASM's quantum-program representation, implemented as Lean data types. It is distinct from Lean's own compiler IR and from the kernel terms that implement those data types.

* What the IR types represent.
:PROPERTIES:
:CHAPTER: 02 / THE PROGRAM AS DATA
:KICKER: 06:00–07:15
:DURATION_SECONDS: 75
:PRESENTER_NOTE: Use this as the reference map for the next three pages. GateDecl.body is Circuit; Program.body and SubroutineDecl.body are Proc.
:END:
=Circuit=, =Proc=, and =Program= are related data types inside the IR. They are not three successive compilation stages.

| IR type | What it describes |
|---------+-------------------|
| Circuit | Compositional circuit structure in gate bodies |
| Proc | Hybrid control flow and effectful operations |
| Program | The compilation unit containing declarations and a process body |

A gate application in a process refers to gate/circuit information; the enclosing Program supplies the declarations.

* Circuit: compositional circuit structure.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 33-45
:CHAPTER: 02 / THE PROGRAM AS DATA
:KICKER: 07:15–08:45
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Define the mathematical correspondence carefully. The constructors retain categorical structure; a denotation and its laws require additional definitions and proofs.
:END:
=Circuit= is an inductive data type for identity, primitives, sequential composition, tensor, permutation, inversion, powers, and control.

Its =dom= and =cod= projections describe ordered wire interfaces. An interface is a list of quantum/classical wire kinds, not a quantum state or a matrix.

\[
\mathrm{dom}(g\circ f)=\mathrm{dom}(f),\qquad
\mathrm{cod}(g\circ f)=\mathrm{cod}(g).
\]

The intended composition also requires matching intermediate interfaces. Lowering checks compatibility; the raw =compose= constructor itself does not carry a proof of that condition.

* Proc: a hybrid computation’s control structure.
:PROPERTIES:
:FILE: QASM/IR/Proc.lean
:LINES: 117-129
:CHAPTER: 02 / THE PROGRAM AS DATA
:KICKER: 08:45–10:00
:DURATION_SECONDS: 75
:PRESENTER_NOTE: Define Proc before relating it to semantics. Explain that gate calls reference declarations instead of directly storing a whole quantum denotation.
:END:
=Proc= describes the control structure of a computation: a sequence, scope, conditional, switch, loop, return, or program end.

Its atomic =Op= values describe effects such as assignment, gate application, measurement, and allocation. This is where quantum requests are combined with classical control.

A =Proc= value is syntax represented as data. Its execution is supplied by the interpreter, while its mathematical execution relation is supplied separately by =Exec= and a semantic =Model=.

* Program: a complete compilation unit.
:PROPERTIES:
:FILE: QASM/IR/Program.lean
:LINES: 33-49
:CHAPTER: 02 / THE PROGRAM AS DATA
:KICKER: 10:00–11:00
:DURATION_SECONDS: 60
:PRESENTER_NOTE: Connect the general definition to the Bell namespace already shown. The distinction between shared representation and a normal-form theorem matters.
:END:
=Program= collects the main =Proc=, gate and subroutine declarations, constants, typed inputs and outputs, target configuration, and source metadata.

=Bell.program= is one such Lean value. The interpreter, diagram renderer, and OpenQASM emitter can consume that same value.

“Canonical IR” names this shared resolved representation in the project. It is not a claim that all equivalent programs have been reduced to a unique mathematical normal form.

* Interpreter: how Program is executed.
:PROPERTIES:
:FILE: QASM/Execution/Interpreter.lean
:LINES: 723-737
:CHAPTER: 03 / EXECUTION AND MEANING
:KICKER: 11:00–12:00
:DURATION_SECONDS: 60
:PRESENTER_NOTE: Describe input, evolving state, and result before discussing implementation abstractions. Keep the explanation at the interpreter entry point.
:END:
An interpreter is an algorithm that reads the program data and performs the corresponding computation.

=QASM.Execution.run= initializes the runtime state, evaluates the main process, and returns final classical values or an execution error. Classical values and qubit bindings are held in the execution state.

The interpreter delegates quantum effects to =QuantumBackend=. Its executable partial definitions and a logical account of execution serve different purposes; their agreement is a separate refinement question.

* Backend: the interpretation of quantum requests.
:PROPERTIES:
:FILE: QASM/Runtime.lean
:LINES: 252-257
:CHAPTER: 03 / EXECUTION AND MEANING
:KICKER: 12:00–13:00
:DURATION_SECONDS: 60
:PRESENTER_NOTE: Define backend independently of the proof-semantics Model. The interface currently has no axioms identifying its operations with ideal quantum mechanics.
:END:
=QuantumBackend= is the execution interface for allocation, unitary application, measurement, reset, and barriers.

A backend implementation chooses how those requests are processed. TraceBackend records them; a simulator or device adapter would provide another concrete execution implementation.

This interface supplies operations and their types. A quantum semantic argument also needs a specification of their behavior and evidence that a chosen backend satisfies it.

* Semantics.Model: supplying a mathematical meaning.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 32-39
:CHAPTER: 03 / EXECUTION AND MEANING
:KICKER: 14:15–15:45
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Read operation and condition as relations, not functions that execute the backend. Explain the choice of State before using a model in a theorem.
:END:
A semantics assigns a mathematical interpretation to program syntax. To define one, we must specify its states, the meaning of operations, and the observations of interest.

The current =Semantics.Model State= is a record parameterizing a relational control-flow semantics. It supplies relations for atomic operations, conditions, iteration domains, and return values, together with binding/restoration functions.

This Model is a semantic parameter, distinct from an executable backend. It does not select a quantum state representation or supply Born-rule measurement probabilities; a quantum interpretation must provide the relevant additional structure.

* Exec and Equivalent: statements about behavior.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 116-125
:CHAPTER: 03 / EXECUTION AND MEANING
:KICKER: 15:45–17:15
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Unpack every argument once. The quantifiers over initial state, final state, and flow are the substance of this particular equivalence definition.
:END:
=Exec M p σ σ' flow= is a proposition: under model =M=, process =p= can execute from state =σ= to state =σ'= with the specified control-flow result.

=Equivalent M p q= says that the two processes have exactly the same such executions:

\[
\forall \sigma,\sigma',f,\quad
\mathrm{Exec}_{M}(p,\sigma,\sigma',f)
\iff
\mathrm{Exec}_{M}(q,\sigma,\sigma',f).
\]

This definition compares finite successful execution relations for a fixed model. Probabilistic observations and divergence-sensitive equivalence require their own semantic treatment.

* What does proving a property mean here?
:PROPERTIES:
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 17:15–18:45
:DURATION_SECONDS: 90
:PRESENTER_NOTE: P is a schematic property, not a new project declaration. Explain that the theorem only establishes the proposition actually stated, under its hypotheses.
:END:
First choose an object and a proposition about it. The object may be a parameter, an IR value, a program family, or a transformation between IR values.

For a property \(P\) of programs, an individual claim has the form \(P(p)\). A family claim can have the form

\[
\forall n\in\mathbb{N},\quad P(\mathrm{program}(n)).
\]

A Lean proof constructs a term of that proposition, checked against the definitions and assumptions it uses. Executing several instances and inspecting their outputs is a different form of evidence.

The next four examples state the object, claim, and proof mechanism explicitly.

* Families: one definition, arbitrary size.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 16-26
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 18:45–20:15
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Distinguish family parameter, runtime input, and size precondition. No numerical representative is used to stand in for every family instance.
:END:
=qasm! Name (n : Nat) { ... }= defines a family indexed by a Lean natural number. The generated =Name.program= is a Lean function from that parameter to an IR program.

For example, =Rotate= retains a symbolic qubit count =n= and has a separate runtime input =theta=. A theorem can quantify over =n= without choosing representative sizes.

The generated =Valid= predicate specifies positive residual sizes. The program data remains definable for all natural numbers, while the execute wrapper requires a proof of the size precondition.

* Proof case 1: the generated I/O widths.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 88-94
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 20:15–21:45
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Explain rfl as definitional equality, not testing. inputType in the displayed equation abbreviates the field projection shown in the actual Lean theorem.
:END:
- Object: the generated data =Copy.program n= for arbitrary =n : Nat=.
- Claim: the first input and output declarations have the resolved type =bit[n]=.
- Proof: =copy_input_width= and =copy_output_width= use =rfl=; the equalities hold by unfolding the generated definitions.

Writing \(\mathrm{inputType}(p)\) for the first input declaration's type, one claim is

\[
\forall n\in\mathbb{N},\quad
\mathrm{inputType}(\mathrm{Copy.program}(n))=\mathrm{bit}[n].
\]

This proves a representation property for every size. It does not assert that execution copies values correctly; that would be a separate behavioral proposition.

* Proof case 2: admissible allocation sizes.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 82-86
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 21:45–23:00
:DURATION_SECONDS: 75
:PRESENTER_NOTE: The theorem quantifies over predecessor n, hence covers every positive size. Do not conflate Valid with a general safety predicate.
:END:
- Object: the generated predicate =Allocate.Valid= on the family parameter.
- Claim: =Allocate.Valid (n + 1)= holds for every natural number =n=, while =Allocate.Valid 0= is false.
- Proof: =allocate_valid= simplifies the predicate and discharges the arithmetic; =allocate_zero_invalid= simplifies the zero case.

This is a proof of a static size precondition. It does not state that a device can allocate that many qubits, that every index is safe, or that the program terminates.

It illustrates how a generated obligation can be stated and discharged separately from an execution.

* Proof case 3: a control-flow transformation.
:PROPERTIES:
:FILE: Tests/Parametric.lean
:LINES: 97-102
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 23:00–25:00
:DURATION_SECONDS: 120
:PRESENTER_NOTE: Show how the general law applies to open program data. This is the main behavioral proof example; keep its model and execution notion visible.
:END:
- Object: the process body \(p_n\) of =Rotate.program n= and the transformed body with a leading =skip=.
- Claim: they satisfy =Equivalent M= for every =n= and supplied relational model =M=.
- Proof: =rotate_skip_neutral= instantiates the general =sequence_skip_left= theorem.

\[
\forall n,M,\quad
\mathrm{Equivalent}_{M}
\bigl(\mathrm{sequence}[\mathrm{skip},p_n],p_n\bigr).
\]

By the previous definition, this compares all initial states, final states, and flow results of those finite executions. It is a behavioral law in the stated model; a connection to the executable interpreter still requires refinement.

* Proof case 4: mapping preserves interfaces.
:PROPERTIES:
:FILE: QASM/IR/Substitution.lean
:LINES: 213-223
:CHAPTER: 04 / PROOF TARGETS AND EXAMPLES
:KICKER: 25:00–26:30
:DURATION_SECONDS: 90
:PRESENTER_NOTE: Connect the theorem back to the Circuit definition. It proves the invariant named in its statement, not every possible correctness property of a transformation.
:END:
- Object: an arbitrary =Circuit s i= and =Circuit.map f g=, which maps its size and integer representations.
- Claim: the mapped circuit has the same domain and codomain interfaces.
- Proof: =Circuit.interfaces_map= uses structural induction; the following lemmas expose each part.

\[
\mathrm{dom}(\mathrm{map}_{f,g}(c))=\mathrm{dom}(c),\qquad
\mathrm{cod}(\mathrm{map}_{f,g}(c))=\mathrm{cod}(c).
\]

Evaluating symbolic sizes and integers is one use of this map. Interface preservation is a structural invariant; equivalence of quantum behavior is a different specification.

* Appendix: what a Bell-state theorem would require.
:PROPERTIES:
:CHAPTER: APPENDIX / OPTIONAL
:KICKER: OPTIONAL / AFTER THE TALK

A prospective specification for the ideal two-qubit circuit fragment is

\[
\llbracket c_{\mathrm{Bell}}\rrbracket |00\rangle
=\frac{|00\rangle+|11\rangle}{\sqrt{2}}.
\]

Here the brackets would need a defined ideal quantum denotation. We would also need to connect the selected circuit fragment to the embedded program, accounting for allocation and the compilation steps.

This is a possible future theorem target, not an existing LeanQASM theorem. A noisy-device claim would additionally require a device/noise model and an appropriate specification.

* Appendix: compiler correctness is another target.

A compiler-correctness statement would relate source and IR semantics, for example

\[
\llbracket \mathrm{lower}(s)\rrbracket_{\mathrm{IR}}
\approx
\llbracket s\rrbracket_{\mathrm{source}}.
\]

Such a theorem must state its accepted source subset, well-formedness assumptions, semantic interpretations, and observations compared by the equivalence.

The current parser/type checker and lowering pipeline construct program data. The proof cases in the main talk do not establish this end-to-end statement.

* Appendix: safety and termination are specifications too.
:PROPERTIES:
:CHAPTER: APPENDIX / OPTIONAL
:KICKER: OPTIONAL / AFTER THE TALK
:DURATION_SECONDS: 0
:END:
A safety theorem could quantify over all executions satisfying input and size assumptions and prove that no invalid index or designated runtime error is reached. A termination theorem would need an appropriate argument for loops and recursion.

=Valid= currently addresses positive residual sizes. Runtime-invalid classical indexing has known incomplete handling; the interpreter uses partial definitions.

The relational proof semantics covers finite successful executions. Those facts make safety, termination, divergence, and interpreter refinement distinct proof targets rather than consequences of the existing examples.
