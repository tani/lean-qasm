An OpenQASM program can be parsed, checked, represented, executed, and inspected inside Lean. This tour follows how =tani/lean-qasm= connects those pieces.

Start with a small Bell circuit, then move inward through typed expressions, categorical circuit structure, structured processes, and compilation. Finally, follow the shared IR back out to execution and presentation.

Thirty source-focused stops sit between this introduction and the closing perspective. Read at your own pace; each stop highlights one part of the design.

* Start with a single import.
:PROPERTIES:
:FILE: QASM.lean
:LINES: 1-15
:CHAPTER: 01 / FIRST CONTACT
:KICKER: THE PUBLIC API
:END:
=import QASM= is the public entry point. It exposes runtime support, canonical IR, parsing, type checking, visualization, and Lean elaboration through their owning modules.

We will begin with a small Bell circuit, then follow the representations and transformations behind it. The entry point re-exports the original namespaces rather than introducing a second facade API.

* Declare a Bell circuit.
:PROPERTIES:
:FILE: Examples/Bell.lean
:LINES: 38-47
:CHAPTER: 01 / FIRST CONTACT
:KICKER: A SMALL QUANTUM PROGRAM
:END:
Write OpenQASM directly inside =qasm! Bell=. This example allocates two qubits, applies =h= to the first, then uses =cx= to entangle the pair.

The =using= clause specifies target widths and the dialect. This declaration connects to IR generation, static inspection, and execution through the generated Lean API.

The intended Bell state is shown below; this example does not itself compute the state vector.

\[
|\Phi^+\rangle=\mathrm{CNOT}(H\otimes I)|00\rangle
=\frac{|00\rangle+|11\rangle}{\sqrt{2}}.
\]

* Inspect without executing.
:PROPERTIES:
:FILE: Examples/Bell.lean

:CHAPTER: 01 / FIRST CONTACT

:END:
=#html Bell.program= derives a static circuit diagram from the declared IR. It does not allocate qubits or execute gates.

Separating a program as data from its execution allows visualization, emission, and interpretation to share one representation.

* Record the effects first.
:PROPERTIES:
:FILE: Examples/Bell.lean
:LINES: 67-71
:CHAPTER: 01 / FIRST CONTACT
:KICKER: DETERMINISTIC TRACE
:END:
Running =Bell.execute= with =TraceBackend.M= records deterministic backend effects. The final =#eval= inspects the allocated qubits.

This is not state-vector simulation. It checks the operations requested by the circuit independently of a particular simulator or quantum device.

* Make types explicit data.
:PROPERTIES:
:FILE: QASM/IR/Type.lean
:LINES: 28-40
:CHAPTER: 02 / THE REPRESENTATION
:KICKER: SCALAR TYPES
:END:
=ScalarTy= represents resolved scalar types: signed integers, angles, complex values, qubits, and more, together with their widths or counts.

The =size= parameter defaults to =Nat= but remains abstract in the grammar. The same representation can therefore express concrete sizes and symbolic compilation sizes.

* Distinguish arrays from references.
:PROPERTIES:
:FILE: QASM/IR/Type.lean
:LINES: 42-46
:CHAPTER: 02 / THE REPRESENTATION
:KICKER: SHAPES AND REFERENCES
:END:
IR =Type= separates scalars, arrays, and array references. Arrays carry their shape; references additionally record mutability, rank, and an optional known shape.

=Option (Array size)= expresses an unknown extent without confusing it with a scalar. Each downstream consumer receives the distinctions it needs.

* An expression has a type and an origin.
:PROPERTIES:
:FILE: QASM/IR/Expr.lean
:LINES: 57-61
:CHAPTER: 02 / THE REPRESENTATION
:KICKER: TYPED EXPRESSIONS
:END:
=Expr= combines a resolved type, an expression node, and a source span. The IR carries analysis results rather than just the shape of the source syntax.

Keeping =SourceSpan= makes it possible to trace the compiled representation back to its source and supports meaningful diagnostics.

* Represent the structure of computation.
:PROPERTIES:
:FILE: QASM/IR/Expr.lean
:LINES: 62-80
:CHAPTER: 02 / THE REPRESENTATION
:KICKER: EXPRESSION NODES
:END:
=ExprNode= distinguishes literals, variables, unary and binary operators, calls, casts, and indexing. Child expressions are themselves typed =Expr= values.

An explicit =unsupported= constructor retains the capability and diagnostic detail instead of silently discarding a feature that a consumer cannot handle.

* Give primitive gates a boundary.
:PROPERTIES:
:FILE: QASM/IR/Primitive.lean
:LINES: 32-46
:CHAPTER: 02 / THE REPRESENTATION
:KICKER: ATOMIC CIRCUITS
:END:
=PrimitiveKind= identifies a primitive circuit. =Primitive= combines its identity and parameters with explicit input and output interfaces.

A gate is more than a string in an instruction list: its circuit boundary is available as structured data.

* Keep composition and tensor distinct.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 33-40
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: CATEGORICAL STRUCTURE
:END:
=Circuit= includes identity, primitives, sequential composition =compose=, and parallel composition =tensor=. Permutations and inverses are distinct nodes too.

The representation retains circuit structure instead of immediately flattening everything into a gate list. Consumers can read the difference between sequencing and parallel placement directly.

* Modifiers wrap a circuit.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 39-45
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: MODIFIERS
:END:
Inversion, powers, and control each retain an inner =Circuit=. In particular, =controlled= separates the control specification from the circuit being controlled.

Even an =unsupported= node records its input and output interfaces. A missing target capability need not erase the surrounding structural boundaries.

* Compute the circuit domain.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 59-69
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: DOMAIN
:END:
=Circuit.dom= obtains the input interface without executing a circuit. Composition takes the first circuit's domain; tensor concatenates both domains.

Inversion delegates to =cod=, while control adds control wires. This total structural definition can also be unfolded in proofs.

For sequential composition, \(\operatorname{dom}(g\circ f)=\operatorname{dom}(f)\). Tensor concatenates the input interfaces:

\[
\operatorname{dom}(f\otimes g)=\operatorname{dom}(f)\mathbin{+\!\!+}\operatorname{dom}(g).
\]


* Read the codomain structurally.
:PROPERTIES:
:FILE: QASM/IR/Circuit.lean
:LINES: 71-81
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: CODOMAIN
:END:
=Circuit.cod= is mutually recursive with =dom=. A composition takes the second circuit's output; an inverse takes the original circuit's input.

These projections do not themselves prove that a composition is well matched. Lowering is responsible for interface compatibility and valid permutations.

* Separate circuits from effects.
:PROPERTIES:
:FILE: QASM/IR/Proc.lean
:LINES: 86-98
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: EFFECTFUL OPERATIONS
:END:
=Op= represents atomic process operations: declarations, assignment, gate application, measurement, reset, allocation, and calls.

Circuit composition alone cannot describe a whole program with classical state changes and measurements. The operation layer supplies the effects that structured control flow refers to.

* Control flow belongs in the IR.
:PROPERTIES:
:FILE: QASM/IR/Proc.lean
:LINES: 117-131
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: STRUCTURED CONTROL FLOW
:END:
=Proc= retains sequences, scopes, branches, switches, and loops. It also represents =breakLoop=, =continueLoop=, =returnValue=, and =endProgram= explicitly.

Rather than immediately translating control flow into the host language, the IR keeps the OpenQASM program structure available as data.

* Collect the compilation unit.
:PROPERTIES:
:FILE: QASM/IR/Program.lean
:LINES: 33-49
:CHAPTER: 03 / CIRCUIT & CONTROL
:KICKER: THE COMPILATION UNIT
:END:
=Program= brings together the version, target configuration, origins, inputs, outputs, constants, gates, subroutines, and process body.

The interpreter, diagram generator, and emitter can all consume this canonical unit without returning to the source AST or Lean elaborator state.

* Read without losing locations.
:PROPERTIES:
:FILE: QASM/Frontend.lean
:LINES: 44-76
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: SOURCE LOCATIONS
:END:
The frontend defines source positions, source spans, parse errors, and token kinds. Tokens carry location information into later stages.

The provenance retained by IR expressions begins here: source-to-IR correspondence is considered from the lexical boundary onward.

* Build the source expression tree.
:PROPERTIES:
:FILE: QASM/Frontend.lean
:LINES: 354-370
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: THE SOURCE AST
:END:
Frontend =Expression= represents the structure of parsed source. Its role differs from the resolved =IR.Expr= we saw earlier.

Successful parsing and a typed, resolved program are separate milestones. Type analysis and lowering connect the two representations.

* Pass analysis results forward.
:PROPERTIES:
:FILE: QASM/Frontend/Typing.lean
:LINES: 303-333
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: TYPE ANALYSIS
:END:
The structures around =TypeAnalysis= describe input and output fields, callable signatures, and gate signatures. They carry information established during type analysis into subsequent stages.

Making this boundary explicit clarifies what lowering may assume about the parsed program.

* Lower into canonical IR.
:PROPERTIES:
:FILE: QASM/Lowering/Program.lean
:LINES: 149-174
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: LOWERING
:END:
=lowerProgram= assembles lowered components into =IR.Program=. Version information, target configuration, origins, and metadata move forward with the program.

The body steps are combined through =programBody=. At this point the compilation unit shared by downstream consumers is complete.

* Keep symbolic sizes open.
:PROPERTIES:
:FILE: QASM/Lowering/Program.lean
:LINES: 187-199
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: OPEN AND CLOSED PROGRAMS
:END:
=template= returns IR parameterized by symbolic =Size= and =Integer=. The closed =program= entry point first rejects remaining parameters, then maps the template into concrete IR.

One structural grammar supports both parameterized program families and closed programs, with distinct public entry points for each.

* Connect the compilation stages.
:PROPERTIES:
:FILE: QASM/Elaboration.lean
:LINES: 293-313
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: THE ELABORATION PIPELINE
:END:
=compileProgram= connects parsing, include expansion, dialect checks, type analysis, and lowering. Failures at each boundary become Lean errors.

The concise =qasm!= command sits above these separate stages. Elaboration orchestrates their work rather than reimplementing every subsystem.

* Generate Lean declarations.
:PROPERTIES:
:FILE: QASM/Elaboration.lean
:LINES: 314-323
:CHAPTER: 04 / FROM SOURCE TO IR
:KICKER: GENERATED LEAN DECLARATIONS
:END:
After lowering succeeds, elaboration generates the Inputs and Outputs structures, the program declaration, and an execute wrapper.

This is where the path returns to =Bell.program= and =Bell.execute=. Embedded OpenQASM becomes declarations that ordinary Lean code can reference.

* Keep execution state separate.
:PROPERTIES:
:FILE: QASM/Execution/Interpreter.lean
:LINES: 46-62
:CHAPTER: 05 / EXECUTION & MEANING
:KICKER: RUNTIME STATE
:END:
=ExecutionState= stores classical values and qubit bindings. Dedicated types distinguish ordinary control flow from interpreter signals.

The IR describes a program; execution state records the information that changes as it runs. This separation lets the same IR be interpreted through different backends.

* Abstract over the backend.
:PROPERTIES:
:FILE: QASM/Execution/Interpreter.lean
:LINES: 723-737
:CHAPTER: 05 / EXECUTION & MEANING
:KICKER: THE INTERPRETER ENTRY POINT
:END:
=run= requires an instance of =QuantumBackend=. It initializes inputs and output defaults, evaluates the body, and returns final classical values or an error.

The concrete meaning of quantum operations lies beyond that backend boundary. TraceBackend is one implementation of this abstraction.

* Describe execution as a relation.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 24-39
:CHAPTER: 05 / EXECUTION & MEANING
:KICKER: A RELATIONAL MODEL
:END:
=Semantics.Model= supplies relations for atomic operations, conditions, iteration domains, and other semantic ingredients. =Flow= distinguishes normal continuation, loop exits, return, and program end.

This model supports reasoning about structured control independently of the executable interpreter. Its definition alone does not establish interpreter refinement.

* Give control flow inference rules.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 44-57
:CHAPTER: 05 / EXECUTION & MEANING
:KICKER: BIG-STEP EXECUTION
:END:
=Exec= relates a process and initial state to a final state and control-flow result. Constructors describe skip, atomic operations, sequences, scopes, and branches.

Condition evaluation has an explicit intermediate state. The model is not restricted to treating a condition as a pure choice of a Boolean value.

* Define the same behavior.
:PROPERTIES:
:FILE: QASM/Execution/Semantics.lean
:LINES: 116-125
:CHAPTER: 05 / EXECUTION & MEANING
:KICKER: OBSERVATIONAL EQUIVALENCE
:END:
=Equivalent= requires agreement of =Exec= for every initial state, final state, and control-flow result, relative to a fixed model.

The following lemma characterizes skip execution. Structured IR is not just something to run: it is also an object on which to state and prove program laws.

* Emit OpenQASM from IR.
:PROPERTIES:
:FILE: QASM/Emit/OpenQASM.lean
:LINES: 603-624
:CHAPTER: 06 / BACK TO THE WORLD
:KICKER: CANONICAL EMISSION
:END:
=emitWithMode= consumes =Program= and renders the header, includes, declarations, and body as OpenQASM. =emit= selects the self-contained mode.

This is emission from canonical IR rather than replay of the original source text. It reads the same program representation as the interpreter, for a different purpose.

* Read, draw, and execute.
:PROPERTIES:
:FILE: QASM/Diagram/Model.lean
:LINES: 56-73
:CHAPTER: 06 / BACK TO THE WORLD
:KICKER: ONE IR, MANY READERS
:END:
=CircuitDiagram= stores wires and presentation items independently of a backend. Operations retain their kind, label, operands, and glyph as rendering data.

Starting with Bell, we have followed types, circuits, control, compilation, and execution. A shared IR sits at the center, read in different ways by the interpreter, emitter, and visualization layer.

* The architecture, in perspective.
:PROPERTIES:
:CHAPTER: 07 / SUMMARY
:KICKER: WHAT WE HAVE FOLLOWED
:END:
The central design choice is a shared canonical IR. Source parsing and type analysis lead into lowering; execution, emission, and diagrams consume the resulting program.

Circuit structure and process control remain explicit. This makes a program available both to executable consumers and to relational reasoning, while keeping the quantum backend as a separate boundary.
